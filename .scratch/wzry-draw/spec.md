# 王者荣耀随机抽签 · 产品说明（Spec）

- 状态：v0.1 已交付并复核通过（tag v0.1.0）；v0.2 视觉与体验升级已实现并通过浏览器验收与代码审查（2026-09-29，CEO 助理独立复核通过）；ticket 10 分路筛选已确认；首页雪花背景增强（ticket 11）待用户确认
- 交付形态：移动端优先的本地单机网页（Nuxt 4 + Nuxt UI 4，PWA 可安装）
- 适配优先级：移动端（竖屏单手）> 平板 > 桌面端（用户 2026-09-29 追加要求）
- 需求澄清：2026-09-29 已通过飞书澄清卡片确认全部 5 项决策，无遗留歧义

## 需求澄清结论（用户已确认）

1. 核心场景：开黑前给每位玩家随机抽一个英雄，一人一英雄，定下本局玩什么。
2. 组队规则：输入玩家名单后随机分成两队，每队人数可调，默认 5v5。
3. 抽签规则：同一次抽签内英雄不重复；允许重抽；保留抽签历史记录。
4. 使用形态：纯本地单机，无需登录、无后端，一台设备上完成抽签。
5. 英雄池：内置当前版本全英雄；并支持自建英雄池，可只抽自己会玩的英雄。

默认交付形态为可安装网页（PWA），手机浏览器打开即用；未要求小程序或原生 App 壳。

## 问题陈述

开黑前，队伍需要快速决定「这局谁玩什么英雄」和「谁跟谁一队」。口头商量容易扯皮、第三方工具操作繁琐或需要网络与账号。需要一款手机上的轻量抽签工具：输入名单，一键抽出不重复的英雄或随机分成两队；过程有仪式感、结果清晰醒目；能重抽、能查历史、能自定义英雄范围；离线可用、无需登录。

## 解决方案

一个移动端优先的本地单机网页应用（可安装为 PWA，仅中文界面）：

### 核心流程 A — 抽英雄

1. 首页点「抽英雄」进入抽英雄页。
2. 编辑玩家名单：默认 5 个槽位，可增删（2~10 人）、可改昵称；空昵称自动填「玩家N」；名单自动记住，下次打开仍在。
3. 选择英雄池：默认「全部英雄」，可切换为某个自定义池。
4. 点「开始抽签」：短暂滚动揭晓动画后展示结果。
5. 结果展示：每位玩家一张醒目卡片，显示英雄名 + 定位标签（对抗路/打野/中路/发育路/游走）。
6. 可对单个玩家「重抽」（其余人结果不变，新英雄不与本局任何其他英雄重复且不等于该玩家原英雄），或「全部重抽」。
7. 完成后自动写入历史记录。

规则约束：同一次抽签内英雄不重复；可用英雄数 < 玩家数时禁止开始并明确提示。

### 核心流程 B — 抽队友

1. 首页点「抽队友」进入抽队友页。
2. 编辑玩家名单（复用同一名单组件），并设置每队人数（1~5，默认 5 → 10 个槽位随设置联动）。
3. 点「开始抽签」：名单随机均分成两队并分栏展示。
4. 边界：名单人数与容量不符时按实际人数均分；奇数时随机一队多 1 人并提示。
5. 可「重新分组」再次随机。
6. 完成后自动写入历史记录。

### 英雄池

- 内置当前版本全英雄静态数据（名称 + 定位标签），随游戏版本人工更新。
- 自定义池：创建 / 重命名 / 删除（删除需确认）；编辑时从全英雄中勾选成员；本地持久化。
- 抽签前可选择「全部英雄」或某个自定义池，选择结果被记住；首次抽签与重抽都只在所选池内进行。
- 英雄列表分路筛选（增强，用户已确认）：英雄池页两处英雄列表（「全部英雄」浏览列表、「编辑成员」弹层选人清单）均支持按分路 tab 筛选（全部 / 对抗路 / 打野 / 中路 / 发育路 / 游走，默认全部）；多分路英雄出现在其所属的每个分路分类中；两处筛选状态互相独立。

### 历史记录

- 抽英雄与抽队友完成后自动留档：时间、类型、参与者与结果。
- 历史页按时间倒序展示，可展开详情，可一键清空（二次确认）。
- 本地保存，最多保留最近 100 条，超出自动丢弃最旧记录。

## 页面结构

- `/` 首页：两个大入口「抽英雄」「抽队友」，次级入口「英雄池」「历史记录」；移除模板演示内容（Counter、InputEntry、Logos、/hi 等）。
- `/hero` 抽英雄页：输入态（名单 + 英雄池选择）与结果态在同一路由内切换。
- `/team` 抽队友页：输入态（名单 + 每队人数）与结果态在同一路由内切换。
- `/pool` 英雄池管理页：全部英雄概览 + 自定义池列表；新建/编辑/删除用弹层完成。
- `/history` 历史页：倒序记录列表 + 详情弹层 + 清空入口。
- `/[...all]` 404 页保留。

设计基调（响应式优先级：移动端 > 平板 > 桌面端）：移动端竖屏单手可操作，除输入昵称外主流程全部触屏完成，主操作按钮置于拇指可及区域；平板端利用更宽屏幕，结果卡片多列排布、内容限宽居中；桌面端为同一版式的居中限宽布局，鼠标点击与键盘操作（回车提交昵称等）均顺畅，不单独开发桌面版式；全尺寸下结果均以大字号卡片醒目展示，深浅色模式均可读；图标统一使用 `<UIcon name="i-lucide-*" />`（CLAUDE.md 约束）。

## 实现决策

- 基座：现有 Vitesse Nuxt 4 模板（Nuxt 4 + Nuxt UI 4 + UnoCSS + Pinia + VueUse + PWA 已就绪）；删除模板演示代码后再建业务。
- 持久化：全部数据仅存本机（localStorage / VueUse `useLocalStorage`），无账号、无后端、不新增 server 路由。
- 状态管理：Pinia 管理玩家名单、自定义英雄池、历史记录；抽签结果页以页面态承载，不额外持久化中间态。
- 英雄数据：集中维护的 TS 静态常量（拼音 id、名称、定位数组、官方数字 id），随游戏版本人工更新；不接远程接口。英雄形象自 v0.2 起接入官方素材，规则见「v0.2 视觉与体验升级」。
- 抽签算法：纯函数（Fisher–Yates 无偏洗牌 + 排除集合），与 UI 解耦；首次抽签与两种重抽、分队算法共用同一套核心逻辑。
- 路由：`/`、`/hero`、`/team`、`/pool`、`/history`；池编辑与历史详情用弹层，不新增路由。
- 响应式：移动优先逐级增强，使用 Nuxt UI / Tailwind 默认断点；大屏下内容限宽居中、结果卡片自动多列；不为平板/桌面单独维护页面或组件分支。
- 品牌：应用名、描述、主题色更新为本应用信息（含 PWA manifest 与页面标题）；沿用模板的 PWA 离线能力与自动更新策略。
- 编码规范：遵循 `@antfu/eslint-config`（无分号、双引号、无尾逗号）；Vue SFC 使用 `<script setup lang="ts">`；类型优先 `interface`；文件名小写连字符。
- 图标：统一 `<UIcon name="i-lucide-*" />`。

## 验收标准（整体）

1. 冷启动（手机浏览器）→ 首页 → 抽英雄（默认 5 人）→ 点抽签 → 5 个互不重复英雄清晰展示，全程触屏单手可完成（输昵称除外）。
2. 单独重抽一位玩家：其余 4 人结果不变，新英雄不与本局任何其他英雄重复且不同于其原英雄；全部重抽可整批刷新。
3. 抽队友：默认 10 个槽位分两队各 5 人；调整为 3v3（6 人）后分队正确；奇数人时分两队人数差 ≤ 1 且有提示。
4. 自定义池：创建 8 个英雄的池并选中抽签，结果全部来自该池；玩家数超过池容量时无法开始并有提示。
5. 历史：抽英雄与抽队友后各产生一条记录，倒序展示、可看详情、可清空；刷新页面数据不丢。
6. PWA：手机浏览器可「添加到主屏幕」，以独立窗口打开显示应用名与图标；断网时核心流程可用。
7. 响应式：375px 竖屏下遍历全部页面无横向滚动、无元素遮挡；平板宽度（768~1024px）下内容限宽居中、结果卡片多列排布且不拉伸变形；桌面宽度（≥1280px）下布局居中不溢出，昵称输入支持键盘回车提交；浅色/深色模式均清晰可读。

## v0.2 视觉与体验升级

背景：v0.1 交付后用户反馈页面「过于简陋」，要求整体视觉/体验升级，并明确推翻此前「不使用真实英雄头像素材」的排除项，要求接入官方英雄形象。用户已授权实现阶段使用设计类 skill 产出视觉方案。

### 设计目标

1. 信息层级清晰：每个页面主次分明，一眼看清该点哪里。
2. 结果卡主视觉：英雄头像 + 大字号名称 + 定位标签。
3. 抽签揭晓更有仪式感：揭晓过程与结果呈现更有张力。
4. 全应用视觉统一：色彩/字号/间距/圆角/阴影有统一语言，延续品牌深蓝 + 金色基调。

### 覆盖页面

首页、抽英雄（输入态 / 结果态 / 揭晓动画）、抽队友、英雄池、历史，及全部弹层与空态。

### 官方英雄形象接入（用户已授权）

- 图源与规格：官方 100×100 小图标（`game.gtimg.cn/images/yxzj/img201606/heroimg/{数字id}/{数字id}.jpg`，133 张全量约 2MB）；英雄名→数字 id 映射来自官网英雄列表页。以上图源已由 CEO 助理实测可用。
- 明确不引入大图 / 皮肤海报（全量 65~130MB）。
- 素材不入库：由脚本 `pnpm heroes` 幂等拉取到 gitignored 的 `public/heroes/`（沿用 `pnpm icons` 的 `scripts/*.mjs` 模式）；下载失败给出提示但不阻断构建。
- `app/constants/heroes.ts` 增加官方数字 id 字段用于拼图片路径；新增 `HeroAvatar` 组件统一展示与降级（图片缺失/失败 → 名称 + 定位占位，不出现裂图）。
- PWA 预缓存需包含 jpg，保证首访在线缓存后断网仍可显示头像。
- 版权：素材版权归腾讯所有，仅本地/个人使用，不随仓库分发。

### v0.2 验收标准

1. 五个页面完成视觉升级、信息层级清晰；首页两个主入口醒目。
2. 抽英雄结果卡以「头像 + 大字号英雄名 + 定位标签」为主视觉；揭晓过程有仪式感。
3. 头像覆盖 133/133；首访在线缓存后断网冷启动头像仍显示；删除 `public/heroes/` 后应用完整可用（降级占位、无报错）。
4. 375px 竖屏无横向滚动；平板（768~1024px）与桌面（≥1280px）布局不退化；深浅色均可读、对比度达 WCAG AA。
5. 触屏优先：可点区域 ≥44px，全流程触屏可完成（输昵称除外）。

### 首页雪花背景（增强，ticket 11）

用户需求：给首页（仅 `/`）加 PixelSnow 像素风 3D 雪花飘落背景（three.js WebGL 着色器，源码已由用户提供并存档）。

- 范围：仅首页；背景为装饰层，不遮挡内容、不拦截点击，其他页面不受影响。
- 深浅色：深色模式用白雪花（官方默认）；浅色模式用金色系且更淡（白雪花在浅色底不可见），保证正文对比度仍达 WCAG AA。
- 动效与无障碍：遵守项目 `prefers-reduced-motion` 约定——用户偏好减弱动效时不加载、不渲染背景。
- 性能：three.js 懒加载、不阻塞首屏；WebGL 不可用或加载失败时静默降级为无背景、页面完整可用。
- 参数：沿用官方推荐默认（flakeSize 0.01 / density 0.3 / speed 1.25 / pixelResolution 200 / variant square / direction 125），仅按深浅色调整颜色与亮度。

验收标准：

1. 首页出现雪花飘落背景且铺满可视区域；所有入口可点击、路由跳转正常。
2. 深浅色下雪花均可见且克制；正文对比度仍达 WCAG AA。
3. `prefers-reduced-motion: reduce` 时无雪花动画（且不加载 three.js）。
4. three.js 懒加载、不阻塞首屏；WebGL 不可用/加载失败时首页完整可用、无报错。
5. 375px 无横向滚动；平板/桌面不退化；其他页面零影响。
6. PWA 离线冷启动不回归；lint / typecheck / test 全绿。

## 测试决策

- 测试哲学：只测外部行为（给定输入 → 可观察输出），不测组件内部实现细节。
- 被测模块（纯逻辑单测）：抽英雄算法（数量正确、无重复、结果均在池内、单人重抽排除集合正确）、分队算法（两队人数差 ≤ 1、成员不重不漏）、英雄池过滤、历史上限裁剪。
- 测试设施：项目当前无测试；本特性引入 Vitest 作为起点，随第一张 ticket 落地。
- UI 层：由开发者在真实浏览器（移动视口）按各 ticket 验收标准逐条走查，不写组件级测试。

## 范围之外

- 账号、登录、云端同步、房间码多人同步（用户明确选择纯本地单机）。
- BP（禁选/选用）模拟与随机分路/位置分配（用户未选择）。
- 抽队友与抽英雄自动串联（一条龙流程，后续可评估）。
- 英雄大图/皮肤海报（bigskin/mobileskin，全量 65~130MB，体积不可接受）；英雄形象仅使用官方 100×100 图标规格，注明来源、仅本地/个人使用、不随仓库分发。
- 微信小程序、原生 App 壳。
- 英雄数据自动更新（随版本人工维护静态数据即可）。
- 多语言（仅中文）。
